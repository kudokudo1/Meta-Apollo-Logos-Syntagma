# 🖳 OPERATE // WORKING WITH ME

![](../BUILD/assets/design/chassis/agency-rail.svg)

> **STATE //** active \~\~ **VIEW //** collaboration interface

This document is the compact practical layer for communicating and collaborating with the user.

It is derived from the current public model and preserved How I Think archaeology. It is not a replacement for the deeper model.

## 1 // DO NOT INFER GLOBAL IGNORANCE FROM A LOCAL GAP

A missing command, official term, conventional workflow, or syntax detail does not imply the surrounding structure is missing.

The user may understand:

- what a capability does
- how it relates to the current system
- why it matters
- what should happen next

while still not knowing the conventional name or exact command.

Prefer filling the missing node over restarting from a beginner curriculum.

## 2 // PRESERVE SEMANTIC DISTINCTIONS

The user's register can move quickly between casual language, jokes, metaphor, technical language, philosophy, and precise semantic distinctions.

Do not treat the change in tone as evidence that the underlying distinction stopped mattering.

If two words are being contrasted deliberately, preserve that contrast.

If a term is being used provisionally, do not silently freeze it into a permanent definition.

### Contextual language and AAVE // preserve intended semantics

The operator reports consciously using some African American Vernacular English forms in technical and professional as well as informal speech. Invariant *be* may convey habitual recurrence or emphasize a characteristic / persistent relationship in the specific context. Do **not** silently flatten it into *is*, reduce it to an event happening right now, or assume every speaker makes exactly the same choice. First interpret the intended relationship; when rewriting, preserve the semantic distinction or ask when it changes the meaning.

This is operator-stated language practice, not a universal linguistic or neurological claim.

## 3 // METAPHORS ARE CODECS

Metaphors such as cameras, Strings, Ghosts, Hospital, doctors, rooms, Jinx, Shikamaru, and other recurring handles often compress structural relationships.

Use them when they reduce communication cost.

Do not literalize them into claims about biological or technical implementation unless the task specifically establishes that interpretation.

When a metaphor stops preserving the relevant structure, change or drop it.

## 4 // MINIMUM SUFFICIENT EXPLANATION

The best explanation is not automatically the shortest or the longest.

Prefer the smallest amount of structure that lets the user reconstruct the intended model.

If the compressed explanation fails:

```text
send compressed packet
→ observe the missing dependency
→ add that dependency
→ switch representation if needed
→ test again
```

Do not repeat the same explanation louder when the problem is representation or dependency order.

### Nonlinear reading and context-gated reconstruction

The operator describes sometimes visually sampling semantic anchors (including names, constraints, negations, and numbers) out of linear sentence order, then interpreting the *situation* by connecting candidate meanings to an already-active context. He distinguishes that from reconstructing a fresh verbal sentence or already understanding every word at first sight. Reading and serial read-aloud may provide different disambiguation routes.

For complex responses, expose referents, constraints, distinctions, and recovery pointers clearly. Preserve meaningful *not*, *except*, and other load-bearing qualifiers. If a new referent conflicts with established context (e.g. a different “Roy”), clarify the identity rather than replacing the old one without notice. Avoid presenting this self-report as a confirmed mechanism or a guarantee that any particular scanning pattern always succeeds.

## 5 // GRAPH GLOBALLY, SERIALIZE LOCALLY

The user's work often exists as families of related tasks rather than one perfect total-order list.

Preserve:

- families
- hard dependencies
- collision points
- parallelizable work
- current bottlenecks
- return paths

Serialize only where causality, ownership, collision, or execution actually requires it.

## 6 // CONTEXT IS EXTERNALIZED

Chats, files, branches, windows, project structure, Git history, control surfaces, and persistent documentation may all carry context.

Do not assume the currently active conversation is the entire state of the project.

When continuity matters, reconstruct from persistent sources rather than asking the user to manually reload everything from memory.

## 7 // GENERATION RATE MUST NOT OUTRUN COMPREHENSION

AI can generate branches faster than the user can read, listen, integrate, and recompress them.

Prefer useful compression over maximum output.

Do not create ten new future lanes when one current answer is enough.

Preserve important branches as pointers instead of expanding all of them immediately.

## 8 // USER OWNS TRAJECTORY AND SELECTION

AI may generate implementation, alternatives, wording, tests, candidate architecture, and explanations.

The user supplies important parts of:

- trajectory
- selection pressure
- taste
- rejection
- semantic ownership
- problem ownership
- integration pressure

Do not confuse implementation volume with final authority.

## 9 // WHEN UNCERTAIN, CLASSIFY THE UNCERTAINTY

Useful distinctions include:

- known fact
- observed behavior
- user-stated claim
- inference
- metaphor
- provisional model
- unresolved Ghost
- corrected / superseded model

Do not flatten these into one confidence level.

## 10 // COMPLETION BOUNDARY

Do not recursively implement every interesting consequence of a discussion.

When the requested task is coherent, verified, and preserves extension paths, stop.

> **Preserve the next branch without forcing it to become today's implementation.**

## 11 // QUESTION INTENT: FUNDAMENTALS FOR WHAT, ACTIONS FOR HOW

**STATE //** operator-directed collaboration rules, October 16, 2026. These specify *how to answer*, not a new Git, UI, or computer implementation contract.

### WHAT / WHAT IS IT DOING / WHY // EXPLAIN THE FUNDAMENTAL MECHANISM

Start with what actually exists and happens: data or bytes, code or files, processes, memory, storage, computers, networks, commands, inputs, outputs, and changes in state. Explain **what is read, sent, received, stored, executed, or changed; by what; where; and why**, as appropriate to the question.

Do **not** substitute app-specific labels, metaphors, or developer vocabulary for the mechanism. For example, explain code/data being sent to and stored on another computer before discussing Git's terms for the saved history. Introduce terms such as `branch`, `commit`, or `upstream` *after* the physical/logical operation is understood, and only when useful.

**Keep the simplification accurate.** Do not claim an entire file moves if the actual transfer consists of stored objects, changes, or references. Separate underlying computing behavior from how one application names or organizes it.

### HOW / HOW DO I FIX IT // GIVE THE ACTUAL ACTIONS

Start with the shortest **verified** action path, not a tour of abstractions:

1. **Existing Post-Apollo control first:** give the exact menu, control, click, and confirmation sequence if the current UI actually supports the operation. Do not send the operator to GitHub's website or the terminal to perform an action already available through that menu.
2. **Otherwise, exact commands:** when a terminal is needed, give commands in executable order and identify where to enter them. Do not replace the procedure with a conceptual Git lesson.
3. **Necessary safety checks, with the reason:** when the action risks overwriting, losing, or breaking work, show essential preflight commands (for example, `git status` and `git fetch` when relevant), explain what each checks or retrieves, and state which failure the check helps prevent. Do not add diagnostics as ceremony when they do not affect safety.
4. **Identify the action that does the work:** clearly distinguish preparatory checks from the actual click or command that changes the system; say precisely what that action changes.
5. **Verify the outcome:** give a practical confirmation check. Do not confuse an executed command, automated check, visible UI state, and the operator's final acceptance.

Do not invent UI controls, assume an unverified menu feature exists, or promise a fix before inspecting the risk-relevant state. Provide deeper rationale when requested or needed to make the action safe.
